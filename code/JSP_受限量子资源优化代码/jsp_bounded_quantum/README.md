# JSP：2×2 结果诊断与受限量子资源扩展

本包将原来的全空间演化改造成可限制资源的局部量子电路实验。已完成离线模拟与编译验证，没有提交 IBM 作业，未消耗 QPU 额度。硬件执行入口尚未经过真实账户端到端验证。

## 1. 原实验说明了什么

上传的实例加工时间为 [[9,6],[7,9]]，机器路线为 [[2,1],[1,2]]。最优工期18。每组1024 shots，tau=20、sf=0.95。

| 层数 | 理想最优解概率 | 硬件最优解频率 | 原硬件双比特门数 | 硬件与理想分布的总变差距离 |
|---|---:|---:|---:|---:|
|1|41.8905%|36.1328%|2|0.0895|
|2|18.3545%|7.2266%|4|0.1774|
|5|2.7172%|25.3906%|10|0.4138|
|10|69.3388%|62.2070%|20|0.1468|

原始 Qiskit 理想分布与独立 NumPy 演化分布吻合，最大误差约8e-16。增加层数并不保证单调提高成功率。5层硬件频率高于理想值不能作为噪声有益或量子优势的证据。对理想分布进行1024次独立抽样的蒙特卡洛检验，四组分布偏差均超出99%参考分位，说明单纯抽样波动不足以解释差异；但缺少当时实际执行的 QPY、布局、校准与完整运行选项，不能进一步归因于某一具体噪声来源。

原日志中的微秒级线路时长不是账户实际消耗，也不包含排队时间。详见 results/upload_audit.json。

## 2. 先优化原有2×2电路

去除每层 barrier，使用 optimization_level=3，允许编译器合并整个二比特酉变换。保持原 tau、离散步数和演化角度，在通用 rz/sx/x/cx 门集中，1、2、5、10层分别得到2、2、3、3个 CX；理想输出分布保持至约1e-15。执行 `python optimize_2x2.py` 可复现，并导出 QPY。

注意：原设备报告20个CZ与通用编译的3个CX不是同一硬件的直接性能比较。实际设备还需重新编译。二比特整体重综合的强压缩效果不能推广为任意规模的常数门数。

另外，把两层的相位和混合角度独立优化，以平均工期为目标，最多256次小型理想模拟评估，本实例获得理想最优解概率0.9999999888，通用编译2个CX。该数值不是硬件成功率；四种候选的工期都已经由经典计算获得，因此也不是量子加速证据。结果与可提交请求在 results/tuned_2x2_ideal_only.json 和 results/tuned_2x2_request.json。

## 3. 更大JSP的重新编码

保持完整的可行机器顺序 π。选择 k 个位置不重叠的相邻交换 S_i，以当前关键路径附近的交换为主，并保留随机探索。量子比特不表示全部调度，只表示本轮是否执行这些交换：

π(x)=S_1^{x_1}…S_k^{x_k}π，x∈{0,1}^k。

每个候选仍然按整个 JSP 的工件约束与机器约束建立有向图，拓扑解码后求最长路径工期 F(x)；有环的候选赋予惩罚 U+1，其中 U 为全部工时之和。这样局部决策的评价包含全局耦合，但本轮候选集合只覆盖很小的邻域。

归一化 f(x)=(F(x)−min F)/max(1,max F−min F)，然后精确展开：

c_A=2^(−k) Σ_x f(x)(−1)^(Σ_{i∈A}x_i)，H_C=Σ_A c_A ∏_{i∈A} Z_i。

从 |+〉^k 出发，每层先施加 exp(−i γ_l H_C)，再施加 exp(+i β_l Σ_i X_i)。多比特 Z 项产生关联相位，配合混合操作可产生纠缠和干涉。不是每个局部工期表都有多体项，也不保证每次电路产生非平凡纠缠；纠缠本身不构成性能证明。

各 Z 项彼此对易，成本相位无需再做项间 Trotter 近似。代码用 CX 奇偶校验链、RZ 与反向 CX 链实现。独立选择浅层角度，避免直接把原先长时间演化粗切成少数几层。

测量后仅接受可行且不劣于当前解的候选，再构造新邻域。硬件解码入口采取更保守的严格改进接受规则。跨轮没有保持全局相干态。这是混合局部搜索；单调不劣不等于收敛到全局最优，也不能继承原全空间模型的能隙或绝热时间保证。

## 4. 可计算的资源上限

每轮经典全局工期评价数为2^k；稀疏图解码每次为O(JM)。成本表存储O(2^k)。不构造 (J!)^M 个全空间状态。

精确相位的一层预路由 CX 上界为：

G(k)=Σ_{r=2}^k 2(r−1) C(k,r)=(k−2)2^k+2。

| 本轮量子比特 k | 候选数 | 两层相位的预路由CX上界 |
|---:|---:|---:|
|3|8|20|
|4|16|68|
|5|32|196|
|6|64|516|

混合层只用单比特门。路由可能增加门数，最终必须检查编译后资源。默认k=4、两层、最多20轮、每轮1024 shots、每轮最多96次理想参数目标评估、全程最多320次候选成本表评价。成本表评价计数不包括初始化、关键路径提取和结果复核；它不是整个程序所有图遍历次数。

硬件编译限制：最多200个双比特门、忽略 delay 后深度不超过600、校准后的单线路调度时长不超过30微秒；不满足则拒绝提交。原型硬限制k≤6，并依据预路由门数预算自动降低k。参数训练发生在经典模拟器中，没有隐含的96轮QPU优化提交。

若R轮各提交一个作业，理想化的量子时间估计为 R·S·(t_circuit+t_init+t_rep)，另加每个作业的固定开销、服务端实际处理与可能的额外电路。hardware_once.py 使用单子作业估算 2秒+S·(上述三项)，并设置服务端 max_execution_time；它是预检和超时设置，不是精确计费保证。排队时长与实际账户用量必须分别记录，以平台返回为准。不能只用 shots×线路微秒数推算额度。

## 5. 离线结果与经典对照

以下为seed=7的一次固定预算运行，并非重复统计或量子加速测试。各方法因采样与并列选择不同，会进入不同邻域。

| 实例 | 经典初始化工期 | 理想量子局部搜索 | 均匀采样局部搜索 | 枚举本轮最优的局部搜索 |
|---|---:|---:|---:|---:|
|3×3示例|15|11|11|11|
|5×5示例|64|56|56|54|
|10×5示例|98|85|85|87|
|50×20数据1|3937|3903|3907|3931|
|50×20数据2|4152|4048|4096|4074|
|50×20数据3|4057|4015|4015|4004|

理想量子模式的本地搜索用时约0.13—0.49秒，不含安装、编译、云端排队及硬件调用，仅代表本环境单次运行。50×20结果说明能对大型实例进行小邻域优化，不能说明全部问题已装入4个量子比特，也不能说明已接近或达到全局最优。

特别重要：本实现为了生成精确相位，已经经典计算了本轮全部候选成本。直接选择本轮最低成本即可获得该邻域的最优结果。量子采样对同一张已知成本表没有更好的成本值可发现。因此这是一套受控硬件研究原型，不是已成立的实用量子加速算法。后续若追求量子优势，需要避免完整成本表枚举，同时把可逆全局评价电路的辅助比特、门数、反计算成本一并计入；不能将这些成本当作免费的 oracle。

## 6. 运行方法

在解压目录创建Python环境，安装依赖后运行：

```bash
python -m pip install -r requirements.txt
python -m unittest test_bounded -v
python optimize_2x2.py
python bounded_qjsp.py search --instance data/demo_3x3.json --bits 3 --layers 2 --rounds 20 --output-dir run3
python bounded_qjsp.py compile --request run3/last_request.json --output-dir compiled3
python bounded_qjsp.py search --instance data/tai50_20_01.txt --bits 4 --layers 2 --rounds 20 --output-dir run50
python benchmark.py
```

search 默认执行本地理想模拟；compile 只编译，均不提交QPU。输出调度CSV可独立检查；last_request.json 是最后一轮的局部问题，不表示整个搜索过程在量子硬件上完成。

可选IBM单作业入口（需自己已保存的账户凭据及正确instance/backend）：

```bash
python -m pip install -r requirements-hardware.txt
python hardware_once.py --request results/tuned_2x2_request.json --backend YOUR_BACKEND --ibm-instance YOUR_INSTANCE --output-dir hardware2
```

上述命令只读取后端并预检；检查 preflight.json 后，在同一命令末尾加 `--submit --max-job-seconds 10` 才会提交一次。入口会记录QPY、物理测量映射、校准、选项、job ID和测量结果。不自动重试、不自动选择账户套餐。真实运行分支尚未端到端验证；请从2×2单作业开始。

硬件结果可作为下一阶段搜索的初始解：

```bash
python bounded_qjsp.py search --instance data/demo_2x2.json --initial-orders hardware2/hardware_result.json --rounds 1 --output-dir next2
```

这条恢复命令接下来仍是本地模拟。项目没有自动连续提交20轮的硬件循环。

## 7. 验证与建议实验顺序

8项单元测试通过，覆盖完整JSP评价、Walsh重建、独立振幅与Qiskit一致性、截断误差界、预算、可行性与单调性、编译后测量映射。额外检查了2×2硬件计数解码、合成后端的调度编译和原算法无barrier重综合。合成后端结果不是实际设备性能。

建议依次进行：原2×2去barrier重编译 → 两层优化角度2×2单作业 → 3×3每轮3比特单作业 → 更大实例固定4比特局部块。每一步都保存理想分布、执行线路、实测分布、最佳可行工期和实际QPU用量，并同时保留经典基线。只有观察到可复现收益后才增加层数、shots或硬件轮数。
